Three open questions I'd been carrying, and how each one settled.

### How Do I Code?

Picking a way to work with an AI agent is choosing along several axes at once:

- **The agent** — Claude Code, Copilot, Codex, or Gemini
- **The surface it runs on** — a terminal, an IDE (VS Code, JetBrains, Cursor), a desktop app, a browser, or a cloud runner
- **The terminal underneath** — iTerm2, Ghostty, tmux, or zellij
- **The session manager** — VS Code Agents, Claude Code's own Agent View, AgentsView, or CodeBurn

Just keeping up with what's available is a full-time job.

[Copilot](https://github.com/features/copilot) was my daily driver for about two years, in the editor and from the CLI, and it's still the best in-flow autocomplete I've used. What changed for me wasn't a harness, though; it was the **_models_**.  In early 2026 the Anthropic ones got very good.

The next step was adopting [Claude Code](https://claude.com/product/claude-code).  This was a major paradigm shift for me: driving code changes entirely through the terminal, not an IDE.

Missing VS Code, I gave [Cursor](https://cursor.com) an evaluation and passed on it. It was very _fast_ in comparison, but that was also the problem: many-thousand-line diffs arriving with very little up-front design or buy-in.  On the terminal side I looked at [herdr](https://herdr.dev) and [agterm](https://agterm.com), and I've been keeping an eye on [opencode](https://github.com/anomalyco/opencode).

When I'm multi-<code class="cpv-claude cpv-inword">clauding</code>, window management becomes a real challenge.  I submitted upstream contributions to the Mission Control replacement [FastMissionControl](https://tomeraviv.github.io/FastMissionControl) and drafted a few features against [iTerm2](https://github.com/gnachman/iTerm2).

### Decision #1 :id=cpv-decision-1
Sticking with Claude Code and iTerm2 tabs.

[beacon](https://chris-peterson.github.io/beacon/#/) makes it easy to keep track of what's happening and jump into the source code or web UIs as needed.

### How Do I Review Changes?

Back in March, I wanted a diff tool made for AI-assisted workflows. I couldn't find one that placed the _human_ as the reviewer and offered an easy way to provide _in-context feedback / change requests_. Annotating a diff in place is what iteration runs on, and nothing I had could do it.

So, I forked `kdiff3` as <code>kdiff<span class="cpv-kdiff-4">4</span></code>, ported it as an Electron app, and renamed it [moor](https://chris-peterson.github.io/moor/#/). Since then, some other OSS has matured, and I've switched to using [revdiff](https://revdiff.com). I like it better as it attaches directly to the originating terminal: fewer disconnected windows to manage.

### Decision #2 :id=cpv-decision-2
Moving moor into maintenance mode;

adopting `revdiff` into [anchor](https://chris-peterson.github.io/anchor/#/guides/configuring).

### How Do I Capture Learnings?

A key part of any successful AI-assisted workflow is to capture and incorporate learnings as feedback to improve the harness.

Thoughtworks' Birgitta Böckeler calls this [the steering loop](https://martinfowler.com/articles/harness-engineering.html): when an issue shows up more than once, you _fix the harness_.

[logbook](https://chris-peterson.github.io/logbook/#/) offers some utilities for capturing mid-session notes for later review. It also has features for teams to store retros in a central location.

In practice, learnings are most useful to a specific individual (the person who burned their hand touching the stove), so a local store is sufficient. And when a learning does repeat, plugins end up being a more efficient mechanism for sharing.

### Decision #3 :id=cpv-decision-3
Putting logbook into maintenance mode;

sticking with a personal `ai-sdlc` repo for retros and AI artifact incubation.

fundamental decisions weren't pinned down.

With these decided, I can now focus on <span class="cpv-echo cpv-echo-key">less</span>,
but <span class="cpv-echo">better</span>.
